1. Introduction
1.1 Purpose
This Software Requirements Specification (SRS) document defines the complete functional and non-functional requirements for HandiLink — a data-driven, on-demand home services marketplace targeted at residents of Quezon City, Philippines. It serves as the authoritative reference for all stakeholders involved in the design, development, testing, and deployment of the HandiLink platform.
1.2 Product Overview
HandiLink addresses a critical trust gap in the local home services market. Homeowners — particularly those new to a neighborhood — currently rely on outdated directories or unverified social media groups when seeking skilled tradespeople. HandiLink resolves this by combining verified worker profiles, a transparent reputation engine, and a streamlined booking flow into a single mobile-first platform.
1.3 Scope
The HandiLink platform encompasses:
A dual-role mobile and web application serving both Customers (homeowners) and Providers (skilled tradespeople)
A backend platform supporting user authentication, booking management, geolocation, payments, and review processing
An administrative dashboard for moderation and system monitoring
Out-of-scope items include major construction services, custom escrow payment systems, and geographic regions beyond Quezon City for the Beta release.

2. Overall Description
2.1 Product Perspective
HandiLink is a standalone platform — not a module of an existing system. It consists of three main components operating in concert:
Mobile Application (iOS and Android) — primary interface for Customers and Providers
Web Application — administrative dashboard and optional desktop access for Customers
Backend API Server — handles all business logic, data storage, third-party integrations, and the Reputation Engine
HandiLink integrates with external services including a payment gateway (e.g., GCash, PayMaya, or Stripe), a mapping API (Google Maps Platform), an SMS/OTP gateway, and cloud storage for photo uploads.
2.2 Product Functions — Summary
The core functional areas of HandiLink are:
Dual-Role User Registration & Verification — secure onboarding for Customers and Providers
Provider Discovery & Search — location-based, filtered search of available Providers
Booking Management — create, confirm, reschedule, and cancel bookings
Real-Time Communication — in-app messaging and booking status push notifications
Transparent Review & Remark System — structured, multi-dimensional post-service reviews
Reputation Engine — automated trust scoring and Verified Badge assignment
Payment Processing — integrated upfront estimates and secure payment capture
Administrative Dashboard — content moderation, dispute resolution, and analytics
2.3 User Classes and Characteristics
2.3.1 Customer
Homeowners or renters who need on-demand home repair or maintenance services. Primary pain points are lack of trust, pricing uncertainty, and difficulty finding reliable help quickly. Expects a simple, intuitive booking flow completable in under three minutes. May have low to moderate technical literacy.
2.3.2 Provider
Independent skilled tradespeople (plumbers, electricians, carpenters, painters, etc.) seeking to grow their client base digitally. Values fair reputation measurement, timely payouts, and a professional profile that showcases their work. Expected to be comfortable with mobile applications.
2.3.3 System Administrator
Anthropic-employed or Group-3-designated personnel responsible for platform health, fraud prevention, content moderation, Provider verification, and dispute resolution. Requires access to backend dashboards and elevated system permissions.
2.4 Operating Environment
Mobile: iOS 15+ and Android 10+ (native applications via React Native or Flutter)
Web: Latest two major versions of Chrome, Firefox, Safari, and Edge
Backend: Cloud-hosted (AWS or GCP), containerized via Docker, deployed with CI/CD pipelines
Database: PostgreSQL (relational data), Redis (caching and sessions), AWS S3 (media storage)
Network: Functions over standard mobile data (3G minimum) and Wi-Fi
2.5 Design and Implementation Constraints
Geographic Beta Constraint: All Beta functionality is limited to Quezon City, Philippines.
Payment Constraint: Only standard integrated gateways are supported; no custom escrow.
Service Category Constraint: Limited to minor-to-moderate home repairs; major construction excluded.
Data Privacy Compliance: All data handling must comply with the Philippine Data Privacy Act (RA 10173).
Connectivity Dependency: Real-time booking updates require internet connectivity; offline mode is limited to viewing saved Provider profiles.
2.6 Assumptions and Dependencies
Users will have smartphones with iOS 15+ or Android 10+.
The third-party payment and mapping gateways maintain at least 99.5% monthly uptime.
Providers will complete the ID and skills verification process before being listed.
Customers will submit honest, detailed reviews after each completed service.
SMS delivery for OTPs is reliable within Quezon City.

4. Non-Functional Requirements
4.1 Performance
NFR-01 [Response Time]: All API endpoints shall respond in under 500ms at the 95th percentile under normal load (up to 500 concurrent users).
NFR-02 [Search Latency]: Provider search results shall render within 2 seconds end-to-end including geolocation filtering.
NFR-03 [Booking Flow]: A Customer shall be able to complete the full search-to-confirmed-booking flow in under 3 minutes under normal conditions.
NFR-04 [Image Upload]: Profile and review photos shall upload and display within 5 seconds on a stable 4G connection.
4.2 Scalability
NFR-05: The backend architecture shall support horizontal scaling to handle up to 10,000 concurrent users without degradation below the performance thresholds in NFR-01.
NFR-06: The database design shall support at least 100,000 registered users and 500,000 bookings without requiring schema redesign.
4.3 Availability and Reliability
NFR-07 [Uptime]: The platform shall achieve at least 99.5% monthly uptime (maximum ~3.6 hours downtime/month).
NFR-08 [Backup]: Full database backups shall be performed daily; point-in-time recovery shall be available for the past 7 days.
NFR-09 [Fault Tolerance]: The system shall gracefully degrade if the payment gateway is unavailable — allowing bookings to be initiated but payment completion deferred — with a clear user notification.
4.4 Security
NFR-10 [Encryption in Transit]: All client-server communication shall use TLS 1.2 or higher.
NFR-11 [Encryption at Rest]: All personally identifiable information (PII) shall be encrypted at rest using AES-256.
NFR-12 [Authentication]: All API endpoints (except registration and login) shall require a valid JWT token. Tokens expire after 24 hours; refresh tokens valid for 30 days.
NFR-13 [Rate Limiting]: Login attempts shall be limited to 5 failed attempts per 15-minute window per IP before CAPTCHA is triggered.
NFR-14 [Data Privacy Compliance]: The system shall comply with the Philippine Data Privacy Act (RA 10173), including the ability for users to request data export and account deletion.
NFR-15 [Vulnerability Management]: A vulnerability scan shall be performed before each production release; critical vulnerabilities must be remediated before deployment.
4.5 Usability
NFR-16 [Onboarding]: A new Customer shall be able to complete registration and place their first booking within 5 minutes without external assistance.
NFR-17 [Accessibility]: The UI shall conform to WCAG 2.1 Level AA guidelines, including sufficient color contrast, scalable text, and screen reader support.
NFR-18 [Language]: The application shall be available in English and Filipino (Tagalog). Language can be toggled in user settings.
NFR-19 [Error Messages]: All error messages shall be written in plain language and include actionable guidance (e.g., &apos;Invalid phone number. Please enter a valid 11-digit Philippine mobile number starting with 09.&apos;).
4.6 Maintainability
NFR-20 [Code Quality]: Backend code shall achieve at least 80% unit test coverage as measured by automated CI pipelines.
NFR-21 [Documentation]: All API endpoints shall be documented in OpenAPI 3.0 format, auto-generated from code annotations.
NFR-22 [Deployment]: The platform shall use a CI/CD pipeline enabling zero-downtime deployments with automated rollback on failure.
4.7 Portability
NFR-23: The mobile application shall be available on both the Apple App Store and Google Play Store.
NFR-24: The web administrative dashboard shall function without installing browser plugins.

6. Key Use Cases
UC-01: Customer Books a Provider
Use Case ID
UC-01
Name
Customer Books a Service Provider
Actor(s)
Customer, Provider, Payment Gateway
Preconditions
Customer is authenticated. Provider has an active, verified profile with available slots.
Main Flow
1. Customer opens the app and enters a service category and current location.
2. System returns a filtered list of nearby Providers sorted by composite score.
3. Customer selects a Provider and reviews their profile, ratings, and reviews.
4. Customer taps &apos;Book Now,&apos; selects a date/time and service type, and enters a description.
5. System displays a price estimate. Customer accepts and selects payment method.
6. System sends booking request to Provider.
7. Provider receives push notification, reviews request, and accepts within 30 minutes.
8. System confirms booking to Customer, deducts payment (held in escrow), and sends both parties a calendar reminder.
Alternative Flow
7a. Provider declines — Customer is notified and prompted to choose another Provider. 7b. Provider does not respond in 30 minutes — booking auto-cancelled; Customer not charged.
Postconditions
A booking record exists in state &apos;Confirmed.&apos; Escrow payment held. Both parties receive calendar/push reminders.
UC-02: Provider Completes Service and Gets Reviewed
Use Case ID
UC-02
Name
Service Completion and Review Submission
Actor(s)
Provider, Customer, Reputation Engine
Preconditions
Booking is in &apos;Confirmed&apos; state. Provider has attended the service appointment.
Main Flow
1. Provider marks the booking as &apos;Complete&apos; in the app.
2. System changes booking status to &apos;Pending Review&apos; and releases a review prompt to the Customer.
3. Customer opens the review prompt within 24 hours.
4. Customer rates the Provider on Punctuality, Technical Skill, and Communication (1-5 stars each).
5. Customer enters a remark (minimum 50 characters) and optionally attaches before/after photos.
6. Customer submits the review.
7. System saves the review, updates the Provider&apos;s aggregate rating, and releases the escrowed payment to the Provider within 24 hours.
8. Reputation Engine re-evaluates the Provider&apos;s eligibility for the Verified Badge.
Alternative Flow
3a. Customer does not review within 24 hours — System sends a reminder push notification. After 72 hours, booking auto-closes without a review; payment still released.
Postconditions
Review is publicly visible on Provider&apos;s profile. Aggregate rating updated. Payment released. Verified Badge status re-evaluated.
UC-03: Provider Onboarding and Verification
Use Case ID
UC-03
Name
Provider Registration and Admin Verification
Actor(s)
Provider, Administrator
Preconditions
Individual has a valid Philippine government ID and proof of trade skill.
Main Flow
1. Provider selects &apos;Register as Provider&apos; and completes registration form.

7. Data Requirements
7.1 Core Data Entities
The following entities constitute the primary data model for HandiLink:
7.1.1 User
Fields: user_id (UUID), role (ENUM: customer|provider|admin), full_name, email, phone_number, hashed_password, profile_photo_url, is_verified, is_active, created_at, updated_at
Constraints: email and phone_number must be unique. role is immutable after registration.
7.1.2 Provider Profile
Fields: provider_id (FK to user_id), bio, trade_categories (array), service_area_radius_km, hourly_rate, flat_rates (JSON), portfolio_photo_urls (array), aggregate_rating, no_show_flag_count, is_verified_badge, government_id_url (admin-only), availability_schedule (JSON)
Constraints: aggregate_rating computed field; not editable directly.
7.1.3 Booking
Fields: booking_id, customer_id (FK), provider_id (FK), service_type, scheduled_at, status (ENUM: pending|confirmed|in_progress|completed|cancelled), description, price_estimate, actual_amount, payment_status, created_at, updated_at
Constraints: scheduled_at must be in the future at creation time. status transitions are enforced by the backend state machine.
7.1.4 Review
Fields: review_id, booking_id (FK, unique — one review per booking), customer_id (FK), provider_id (FK), rating_punctuality (1-5), rating_skill (1-5), rating_communication (1-5), remark (min 50 chars), photo_urls (array, max 5), provider_response (max 300 chars), is_flagged, created_at
7.1.5 Message
Fields: message_id, booking_id (FK), sender_id (FK), content, is_redacted, sent_at
Constraints: content scanned on save; PII patterns replaced with [REDACTED].
7.1.6 Payment Transaction
Fields: transaction_id, booking_id (FK), gateway (ENUM: gcash|paymaya|stripe), amount, platform_fee, provider_payout, status (ENUM: held|released|refunded|failed), gateway_reference_id, created_at, updated_at
7.2 Data Retention Policy
Active user data: retained indefinitely while account is active.
Messages: retained for 6 months post-booking completion, then archived.
Review photos: retained for 2 years, then purged from CDN.
Payment transactions: retained for 7 years to comply with Philippine BIR regulations.
Deleted accounts: PII anonymized within 30 days of deletion request; transaction records anonymized but retained for compliance.
8. System Constraints and Risks
8.1 Constraints Summary
Type
Constraint
Implication
External
User Dependency
Platform trust quality depends on customers submitting honest, detailed reviews. Minimum character count and photo prompts mitigate but cannot eliminate this risk.
External
API Stability
Payment and map gateways may have outages. Graceful degradation and fallback messaging are required in the booking flow.
External
Offline Safety
Digital ID verification reduces but cannot eliminate the risk of real-world misconduct. Physical safety features (e.g., share ETA) are recommended as future enhancements.
Intentional
Geographic Scope

Intentional
Service Category
Only minor-to-moderate home repairs. Major construction services are excluded.

Payment Handling
Standard gateway integration only. Custom escrow logic is out of scope for Beta.
8.2 Key Risks and Mitigations
Review Gaming: Providers might solicit fake positive reviews. Mitigation: Reviews only unlocked for verified, completed bookings. Admin tools to detect anomalous review patterns.
Provider Supply in Beta: Initial lack of Provider supply in QC could harm user experience. Mitigation: Pre-launch Provider recruitment campaign targeting trade schools and informal networks in QC.
Payment Fraud: Disputed transactions or chargebacks. Mitigation: Escrow model, booking documentation via chat logs and photos, chargeback dispute process with gateway.
Data Breach: PII exposure. Mitigation: AES-256 encryption at rest, TLS in transit, regular penetration testing, DPA-compliant breach notification process.
